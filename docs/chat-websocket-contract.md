# LearM — Chat WebSocket v1

Дата: 30 сентября 2026. Фронтенд реализован под этот контракт. Это новый контракт для реализации/согласования с бэкендом, а не описание уже проверенного серверного WebSocket.

## Подключение и включение

Предлагаемый endpoint: `wss://<домен-api>/ws/chats`.
Для локальной разработки: `ws://localhost:8000/ws/chats`.
Конкретный адрес сервера должен подтвердить бэкендер.

На фронтенде задать в `.env.local` и пересобрать/перезапустить приложение:

```dotenv
NEXT_PUBLIC_CHAT_WS_URL=wss://<домен-api>/ws/chats
```

По умолчанию настройка пустая: WebSocket отключён, чат работает через REST. URL не вычисляется из адреса REST API. HTTPS-фронтенд принимает только WSS. Никаких токенов в URL, query, cookies или subprotocol для этого контракта. Не Socket.IO — обычный WebSocket с текстовыми JSON-сообщениями.

Один сокет на авторизованную вкладку, сразу для всех доступных пользователю чатов. Не нужны `subscribe`, `join` или отдельный сокет на каждый чат. После создания нового чата/добавления участника сервер сам обновляет доставку. В фоновой вкладке сокет закрывается, после возвращения подключается снова.

## Авторизация

Сразу после `open` клиент отправляет текущий access token:

```json
{ "type": "auth", "access_token": "<access_token>" }
```

Сервер проверяет токен, пользователя и его активность, подключает доставку событий и отвечает:

```json
{ "type": "auth.ok" }
```

До `auth.ok` фронтенд игнорирует события чатов. Сервер не должен отправлять приватные данные до авторизации. Если за 5 секунд не получен auth — закрыть сокет кодом `4401`. Клиент ждёт `open`/`auth.ok` не более 10 секунд.

Токен обновляется существующим REST-механизмом `/auth/refresh`, refresh token в WebSocket никогда не отправляется. При истечении access token сервер закрывает сокет с `4401`: клиент один раз обновляет токен и подключается заново. Повторный `4401` до успешного `auth.ok` останавливает этот цикл попыток; REST продолжает работать. `4403` также останавливает попытки текущего цикла. Новый вход/возврат во вкладку может начать новый цикл.

При выходе или смене аккаунта соединение закрывается, запоздалые события старой сессии игнорируются. Бэкенд также должен закрывать соединения при отзыве сессии/деактивации пользователя. Проверять Origin по разрешённым адресам приложения, не записывать auth payload и токены в логи.

## Клиент → сервер

В v1 клиент отправляет только `auth` и `ping`:

```json
{ "type": "ping" }
```

После авторизации ping отправляется раз в 25 секунд, затем ожидается pong не более 10 секунд. Это прикладные JSON-сообщения, не протокольные WebSocket Ping/Pong frames.

**Событий `message`, `message.send`, `typing.start`, `typing.stop` в этой версии нет.** Индикатор набора текста пока не реализован. Запись сообщения выполняется через REST один раз, без дублирования в WebSocket и без автоматического повтора после обрыва.

## Сервер → клиент

Каждый блок ниже — отдельный текстовый JSON-frame. UUID ниже приведены как примеры.

Ответ на ping:

```json
{ "type": "pong" }
```

Новое сообщение:

```json
{
  "type": "message.created",
  "chat_id": "a56aa3d6-39bc-4450-95f9-b2de44a99054",
  "message_id": "47c05f2a-d4e4-4909-bbaf-1086053f204a"
}
```

Редактирование:

```json
{
  "type": "message.updated",
  "chat_id": "a56aa3d6-39bc-4450-95f9-b2de44a99054",
  "message_id": "47c05f2a-d4e4-4909-bbaf-1086053f204a"
}
```

Удаление:

```json
{
  "type": "message.deleted",
  "chat_id": "a56aa3d6-39bc-4450-95f9-b2de44a99054",
  "message_id": "47c05f2a-d4e4-4909-bbaf-1086053f204a"
}
```

Изменение состояния прочтения:

```json
{
  "type": "message.read",
  "chat_id": "a56aa3d6-39bc-4450-95f9-b2de44a99054",
  "message_id": "47c05f2a-d4e4-4909-bbaf-1086053f204a"
}
```

Создание/изменение чата или его участников:

```json
{ "type": "chat.updated", "chat_id": "a56aa3d6-39bc-4450-95f9-b2de44a99054" }
```

Удаление чата или отзыв доступа у получателя:

```json
{
  "type": "chat.access_revoked",
  "chat_id": "a56aa3d6-39bc-4450-95f9-b2de44a99054"
}
```

Ошибка протокола/авторизации:

```json
{
  "type": "error",
  "code": "UNAUTHORIZED",
  "message": "Authentication required"
}
```

`code` и `message` — строки. Фронтенд не показывает произвольный серверный текст пользователю и не исполняет его. Ошибки авторизации/доступа должны сопровождаться закрытием `4401`/`4403`; один `error` не запускает refresh. Неизвестные события, невалидные UUID, бинарные frames и строки длиннее 16384 символов игнорируются.

## Семантика доставки

- События отправляются **после успешного commit** REST-операции. Они означают «данные изменились», а не содержат всю модель сообщения.
- `chat_id`, `message_id` — строки UUID, как в REST. Фронтенд повторно получает актуальные данные по REST и использует существующий `MessageResponse`.
- Message-события получают только текущие участники чата, включая вкладки отправителя. При добавлении участника ему и другим участникам отправляется `chat.updated`.
- При удалении участника сначала отозвать серверный доступ, исключить его из доставки и отправить ему `chat.access_revoked`; остальным — `chat.updated`. При удалении чата отправить `chat.access_revoked` бывшим участникам. Фронтенд отменяет запросы, очищает данные этого чата и выходит из открытого диалога.
- Проверка прав выполняется на сервере и для REST, и для доставки событий. Фильтрация UI не заменяет её.
- `message.read` уведомляет об изменении текущего REST `is_read`. Отдельные статусы прочтения каждым участником группы в v1 не добавляются.
- Повторные события допустимы. Клиент объединяет обновления запросов в окно 100 мс. Источник истины — REST; последовательные номера и replay в v1 не нужны.
- После каждого `auth.ok`, включая переподключение, фронтенд обновляет активные запросы чатов, сообщений, участников и реакций. Неактивные запросы помечаются устаревшими и загружаются при открытии.
- Сохраняется резервный REST polling: 2 секунды для открытого диалога, 5 секунд для списка чатов/других подписанных списков сообщений. В фоне polling приостановлен.

## REST остаётся прежним

| Операция       | Метод и путь                                        | Тело                        |
| -------------- | --------------------------------------------------- | --------------------------- |
| История        | `GET /chats/{chat_id}/messages`                     | —                           |
| Отправка       | `POST /chats/{chat_id}/messages`                    | `{"content":"Привет"}`      |
| Редактирование | `PATCH /chats/{chat_id}/messages/{message_id}`      | `{"content":"Новый текст"}` |
| Удаление       | `DELETE /chats/{chat_id}/messages/{message_id}`     | —                           |
| Прочтение      | `PATCH /chats/{chat_id}/messages/{message_id}/read` | —                           |

Ответы REST продолжают соответствовать существующему OpenAPI. Новых WS-событий для реакций в v1 нет; они остаются на REST.

## Переподключение

При обычном обрыве: задержки 1, 2, 4, 8, 16, 30 секунд, далее максимум 30 секунд, плюс случайные 0–499 мс. После `auth.ok` задержка сбрасывается. Отсутствие pong также вызывает переподключение. Пауза при offline/скрытии страницы, восстановление при online/возвращении. На восстановлении нет повторной отправки сообщений.

## Совместная приёмка после реализации бэкенда

1. Два аккаунта в разных браузерах: новое сообщение, редактирование, удаление, прочтение вызывают ожидаемые WS-события после commit.
2. Проверить Network → WS → Messages: REST polling сам по себе может скрыть отсутствие событий.
3. Добавить/удалить участника: новый участник видит чат, удалённый теряет доступ и больше не получает события.
4. Отключить сеть, отправить сообщение вторым аккаунтом, восстановить сеть: актуальная история появляется после auth.ok.
5. Истечь токен: 4401 → REST refresh → новое соединение → auth.ok. Повторное отклонение не вызывает бесконечный refresh.
6. Выйти и войти другим аккаунтом: старый сокет закрыт, данные прежнего аккаунта не появляются.
7. Не отвечать на ping: клиент переподключается. Без WebSocket чат продолжает работать через REST.

Реальная серверная доставка пока не проверена: нужен backend, реализующий этот контракт, и подтверждённый URL.
